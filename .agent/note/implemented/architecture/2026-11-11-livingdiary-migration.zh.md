# Agent Note: LivingDiary 迁移至 ChatLuna v2

Status: implemented

## 问题

LivingDiary 会向真实 QQ 空间写入内容。ChatLuna v2 工具可以指定同轮另一名发言人，重复轮询也会再次遇到同一条动态或评论。这两条路径都需要明确由谁决定是否写入以及写到哪里。

## 决策

对话发布工具按实际请求者授权，直接发布其提交的正文。后台任务使用配置的空间人设：日记读取 LivingMemory 并调用日记模型；自动互动使用独立的互动模型和 QQ 白名单。后台任务的人设不随最近发言的群聊切换。

首次初始化和续绑均把 Cookie 与解析出的 QQ 账号一起交给 SDK。读请求可在续绑后重放一次；已提交的写请求不自动重发。

日记取服务器本地零点至本次运行开始时新建的活跃记忆，按创建时间取最近的配置条数，再从早到晚交给模型。

启动轮询时，现有动态和评论只作为历史记录。机器人自有动态下的新评论，以及好友动态中机器人自己发起的一级线程里的新回复，才进入回复决策。模型决定是否写、写什么；插件从完整评论快照确定目标并调用 SDK。

本人动态从绑定账号的个人主页读取，SDK 的空间首页也含好友动态。只采纳正常结束的模型调用所给出的写入决定。自动读取配图只访问 QQ 空间图片域名，每次重定向都重新检查；读取失败的图片也计入同一份流量额度。

## 考虑过的替代方案

**按工具调用中指定的发言人授权。** 请求者可以借用同轮其他人的发帖权限。

**只读第一页记忆或按更新时间选取。** 今天编辑过的旧记忆会挤占今天实际新建的条目。

**重启后补扫停机期间的互动，或重试结果未知的写入。** 这会造成过时或重复的公开回复。轮询状态只在插件实例存活期间保留。

## 影响

切换请求者后，模型请求缓存仍可含有发布工具的定义，实际执行时仍须通过当前请求者的授权检查。结果不明的写入可在状态报告中查看；评论快照不完整时，留到后续轮询再做决策。

## 验证

- [x] 空间命令与工具：验证了请求者授权、SDK 账号绑定和写入次数。OneBot 已实读一条自己的动态；Milky 有适配器测试。
- [x] 每日日记：测试覆盖手动与定时执行、两类预设、以本地日界和创建时间选取记忆、只发一次。
- [x] 自动互动：通过模拟动态与模型供应商验证了启动时跳过历史、白名单、线程归属、写入上限和取消。未向真实 QQ 空间写入。
